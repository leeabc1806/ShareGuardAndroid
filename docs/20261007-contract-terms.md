# ShareGuard 전자 대여 계약 조항 v1.0 · 2026-10-07

## 적용 순서

1. 기존 DB에는 **`ShareGuardAndroid/database/schema.sql`을 다시 실행하지 않습니다.** 새 DB용 기본 스키마에는 V8의 새 칼럼·제약조건을 반영했으며, 그 뒤에도 V1~V8을 순서대로 적용해야 계약 RPC·Storage 정책이 완성됩니다. 기존 Flyway V1~V7은 수정하지 않았습니다.
2. 기존 스키마와 V1~V7이 적용된 DB에 `ShareGuardAndroid/database/migrations/20261007_contract_terms.sql`을 적용합니다. **ShareGuard 운영 Supabase에는 2026-10-08에 이미 적용했으므로 SQL Editor에서 다시 실행할 필요가 없습니다.** 같은 내용의 서버 자동 마이그레이션은 `backend/src/main/resources/db/migration/V8__contract_terms.sql`입니다. 서버 Flyway 이력은 현재 V7까지이며, 새 서버 코드를 배포하면 V8을 실행하도록 반복 실행에 안전하게 작성했습니다.
3. 서버를 새 코드로 배포하고 앱을 새 APK로 업데이트합니다. 양쪽이 같은 V8 스키마를 사용해야 물품 등록/계약 조회/서명이 작동합니다. 운영 DB 백업 후 테스트 계정 두 개로 승인→결제→특약→양측 서명→PDF 재생성을 확인합니다.
4. 기존 서명은 시간만 저장되어 PNG가 없는 상태입니다. V8은 과거 서명을 추정·복원하지 않으며, 과거 서명 계약에는 새 조항을 소급 표시하거나 새 PDF를 만들지 않습니다. 한쪽만 과거 방식으로 서명한 계약은 새 서명 RPC도 차단하므로 운영자가 별도 처리해야 합니다.

SQL Editor에서 시크릿 키나 DB 비밀번호를 입력할 필요가 없습니다. 앱에는 Supabase 공개 키만 사용합니다.

## 변경 내용

| 영역 | 변경 |
| --- | --- |
| 조항 | `ContractTerms.kt` 한 곳에 버전·시행일·15개 조항·숫자 기준을 정의했습니다. 연체료 상한과 취소 공제 계산은 **계약 표시·테스트용**이며 결제 요청을 만들지 않습니다. |
| 물품 | 구성품·기존 하자·물품 가액을 선택 입력합니다. 기존 사진 선택·카테고리 변경 시 입력값을 보존합니다. DB는 nullable, 글자 수/비음수 제약을 적용합니다. |
| 계약 snapshot | 승인 시 물품·당사자 닉네임/인증/신뢰점수·보증금 감면 정보와 조항 버전을 기록합니다. 첫 서명 후 DB 트리거가 snapshot 및 특약 변경을 막습니다. |
| 특약 | 계약 당사자만 draft·양측 미서명 상태에서 최대 500자를 수정합니다. 다른 사람 또는 첫 서명 이후에는 거부합니다. |
| 서명 | 당사자별 PNG를 비공개 `contract-signatures/{contract_id}/{owner|borrower}.png`에 저장합니다. 서버 RPC가 당사자의 본인인증 상태와 해당 파일을 확인한 뒤 서버 시각과 정규화된 snapshot의 SHA-256을 남깁니다. 제3자는 버킷을 읽거나 쓸 수 없습니다. |
| 앱 흐름 | 조항 전문을 스크롤로 보여주고 동의 체크 전에는 서명 패드가 비활성화됩니다. 상대방 기기에서도 서버 snapshot/서명 PNG를 조회해 PDF를 새로 만들 수 있습니다. |
| PDF | A4 자동 페이지 넘김, 줄바꿈, 페이지 번호·계약번호·중개 고지, 양측 서명란, KST 서버 서명 시각, snapshot 해시·버전·PDF 생성 시각을 표시합니다. |

결제 주문번호·승인 시각은 V8의 읽기 전용 RPC가 **계약 당사자에게만** 제공합니다. 결제 키·PG 원문은 공개하지 않습니다. 아직 결제 주문 정보가 없는 계약은 PDF에 `미기록`으로 표시합니다. 대여 전 상태 사진 장수는 PDF 생성 당시의 최신 기록이며 승인 snapshot 해시에는 포함되지 않음을 함께 표시합니다.

해시는 **계약 snapshot JSON**의 해시이지 PDF 파일 자체의 해시가 아닙니다. 최상위 `hash` 키를 제외하고 JSON 객체의 키를 재귀적으로 정렬해 SHA-256을 계산합니다. 첫 서명 이후 두 당사자는 같은 값을 공유합니다. 실명·전화번호는 PDF에 넣지 않습니다.

## 계약 문구와 실제 서버 동작의 차이 — 데모 전에 반드시 고지

- 연체료(1시간 유예·지연 1일당 하루 대여료·보증금 상한)는 계약 조항과 계산 상수만 있습니다. **서버 청구·보증금 공제는 아직 구현하지 않았습니다.**
- 시작 2일 전/1일 전/당일 취소 공제 30%도 계약 문구만 있습니다. **결제 취소·위약금 계산에 연동되지 않았습니다.**
- 반납 뒤 대여자 이의 제기 24시간이 지나면 환급 대상이라는 조항은 있지만 **자동 환급 스케줄러는 없습니다.** 기존 수동 환급/분쟁 처리를 그대로 사용합니다.
- QR 실패 시 수동 검수, 3일 연락 두절 신고·보류, 6개월 손해배상 기한, 기록 5년/3년 보존도 현재 계약 문구이며 별도 운영 절차·서버 강제가 필요합니다.
- 승인 시점의 대여 시작·종료값은 현재 앱에서 날짜 중심입니다. 인도/반납의 실제 시각은 QR 기록을 따라야 하며, 일시 선택·표시는 별도 개선이 필요합니다.
- 서명 후 생성한 PDF는 현재 앱 기기에서 재생성합니다. 서버가 PDF 원본을 보관하거나 PDF 자체에 전자서명 인증서를 발급하는 것은 아닙니다.

따라서 현재 PDF를 실제 완결된 청구·환급 서비스의 법적 증빙이라고 홍보하지 않습니다. 개인 간 거래에 전자상거래법상의 통신판매중개 규정이 어떻게 적용되는지, 취소 조항과 개인정보 동의·보존 운영이 적법한지는 운영 전 법률 검토가 필요합니다.

## 검증

JDK 17(`C:\Users\dollq\.jdks\jbr-17.0.14`)로 다음을 실행합니다. Windows에서 프로젝트 경로의 한글 때문에 Gradle 테스트 클래스 로딩이 실패하면 영문 경로의 임시 junction에서 같은 저장소를 실행합니다.

```powershell
$env:JAVA_HOME="$env:USERPROFILE\.jdks\jbr-17.0.14"
cd ShareGuardAndroid
.\gradlew.bat testDebugUnitTest assembleDebug lintDebug
cd ..\backend
.\gradlew.bat test bootJar
```

`tools/test_feature_database.py`는 운영 Supabase에 연결하지 않고 격리된 PostgreSQL DB에서 V8 반복 실행, 특약·서명 이미지 접근 권한, 서명 후 고정, 기존 V3 제한을 검증합니다. `tools/LocalSql.java`는 이 PC처럼 `psql.exe`가 없을 때만 쓰는 로컬 JDBC 실행기입니다.

2026-10-08 로컬 결과: Android 단위 테스트 29개·서버 테스트 37개 통과, 로컬 DB 검사 53개 통과, `assembleDebug`·`lintDebug`·`bootJar` 성공. Lint 오류는 0개이며 기존 경고는 남아 있습니다. Android 에뮬레이터에서 실제 `ContractPdfExporter`로 만든 [샘플 PDF](../output/pdf/shareguard-contract-sample-20261007.pdf)는 A4 3쪽입니다. 세 쪽을 이미지로 렌더링해 제목·조항·두 서명란·해시·머리글/바닥글의 잘림과 겹침이 없음을 확인했습니다. 이 샘플의 인물·주문·서명은 모두 예시입니다.

운영 Supabase에는 2026-10-08에 V8을 적용했습니다. 새 물품 열의 공개 키 REST 조회는 HTTP 200이며, DB에서 4개 제약조건·비공개 서명 버킷·3개 Storage 정책·계약 RPC 권한을 확인했습니다. 다만 **실제 두 계정·결제·PASS·양측 서명·상대방 기기 PDF 재생성의 종단 간 검증은 아직 하지 않았습니다.** 확인 당시 v1.0 계약 6건 중 서명된 건은 0건이고 서명 PNG도 0개였습니다. 운영 DB 백업 및 테스트 계정 확인 전에는 완료로 간주하지 마세요.
