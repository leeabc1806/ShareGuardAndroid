## 실기기 연결

현재 로컬 설정에는 이 PC에서 확인한 Wi-Fi 주소 `http://192.168.0.12:8080/`를 넣었습니다.
PC 주소는 Wi-Fi 환경에 따라 달라질 수 있습니다. 휴대폰과 PC를 같은 네트워크에 연결하고, 새 주소는 저장소 루트에서 다음처럼 설정합니다.

```powershell
.\tools\Configure-DeviceServer.ps1 -BaseUrl 'http://192.168.0.12:8080/'
```

`ShareGuardAndroid/local.properties`의 SDK 경로·공개 앱 키는 보존합니다.
`TOSS_CONFIRM_URL`은 비워 두면 `SHAREGUARD_API_BASE_URL` + `/api/v1/payments/toss/confirm`으로 생성됩니다.
주소 변경 후 APK를 다시 빌드하고 재설치해야 합니다.

서버 실행 후 휴대폰 브라우저에서 `http://192.168.0.12:8080/actuator/health`의 `UP`을 확인합니다.
PC에서는 열리지만 휴대폰에서 열리지 않으면 같은 Wi-Fi인지, 공유기의 단말 간 통신 제한과 Windows 개인 네트워크의 서버 포트 허용을 확인합니다.
HTTP는 디버그 앱의 로컬 테스트용이며 배포 주소는 HTTPS로 설정합니다.

USB 디버깅을 쓸 경우:

```powershell
adb reverse tcp:8080 tcp:8080
.\tools\Configure-DeviceServer.ps1 -BaseUrl 'http://127.0.0.1:8080/'
```

`10.0.2.2`는 Android 에뮬레이터에서 PC에 접속할 때 쓰는 주소입니다.

## 팀 DB·결제 서버 실행

`backend/README.md`의 환경변수를 실제 프로젝트 값으로 설정합니다. 특히 다음 값이 필요합니다.

- `SUPABASE_DB_URL`, `SUPABASE_DB_USER`, `SUPABASE_DB_PASSWORD`
- `SUPABASE_JWKS_URI`: 앱과 같은 Supabase 프로젝트의 JWT 공개키 주소
- `TOSS_SECRET_KEY`: 앱의 토스 클라이언트 키와 같은 테스트 상점의 서버 키
- `TOSS_WEBHOOK_PATH_TOKEN`: 직접 생성한 비밀 경로 값
- `PORTONE_API_SECRET`, `PORTONE_STORE_ID`: 본인인증 검증용

서버 비밀키와 DB 비밀번호는 APK나 Git에 넣지 않습니다. 환경 점검 스크립트는 값 자체를 출력하지 않습니다.

```powershell
cd backend
.\tools\Check-BackendEnvironment.ps1
.\gradlew.bat bootRun
```

기존 `ShareGuardAndroid/database/schema.sql`이 설치된 DB에서 Spring 시작 시 Flyway V1~V3를 적용합니다.
최초 DB에는 해당 기본 스키마를 먼저 설치해야 합니다. 기존 DB에 초기 스키마 전체를 다시 실행하지 마세요.
V3 이후 예전 초기 스키마의 권한·함수를 다시 덮어쓰면 이전 데모 경로가 열릴 수 있습니다.

시작 후 별도 터미널에서:

```powershell
.\tools\Check-BackendEnvironment.ps1 -CheckHealth
```

Supabase SQL Editor 또는 관리자 DB 연결에서 `backend/tools/verify-migrations.sql`을 실행합니다.
V1·V2·V3 성공 여부, 서버 전용 테이블 존재, 데모 RPC 실행 불가, 직접 결제 상태 수정 불가를 확인할 수 있습니다.

## 변경된 API

- `GET /api/v1/payments/{reservationId}`: `status`, `approvedAmount`, `refundedAmount`, `refundableAmount`, `refundAllowed` 반환. 당사자 또는 관리자만 조회 가능.
- `POST /api/v1/payments/{reservationId}/refund`: `amount`, `reason` 전달. 서버에서 완료 상태·분쟁·차감·이미 환급한 금액을 재검사.
- `POST /api/v1/qr/verify`: 기존 `payload`, `latitude`, `longitude`에 **contractId, action** 추가. 새 앱과 새 서버를 함께 적용해야 함.
- 반납 QR 성공 응답은 환급 성공을 의미하지 않음. `refunded`는 서버에서 확인한 보증금 전액 환급 상태. 차감이 있으면 `partially_refunded`로 남을 수 있음.
- 일반 토스 승인만으로 별도 에스크로 계약 체결을 증명하지 않으므로 승인 알림에는 확인된 결제 사실만 표시.

## 실기기에서 남은 확인

1. 실제 서버 환경변수 설정 후 Flyway V3까지 성공, 휴대폰에서 health `UP` 확인.
2. 서로 다른 실제 계정 2개로 로그인. 이름·인증 배지·점수·이력 확인, 로그아웃/재로그인 시 이전 계정 정보가 남지 않는지 확인.
3. 테스트 결제: 승인 성공과 승인 실패 각각 확인. 클라이언트/서버 키는 같은 테스트 상점 값 사용.
4. 양측 서명·사진 등록 후 상대방 QR 스캔. 자기 QR·다른 계약·재사용·만료 QR은 거래 상태를 바꾸지 않는지 확인.
5. 반납 직후에는 환급 대기로 표시되는지 확인. 환급 요청 성공 시 토스 테스트 내역과 서버 누적 환급액 비교.
6. 서버 연결을 끊거나 환급을 거부시켜도 환급 완료로 바뀌지 않는지 확인. 연결 복구 후 새로고침.
7. 분쟁 중 환급 차단, 관리자 차감 결정 이후 남은 금액만 환급되는지 확인.

로컬 테스트 통과와 팀 DB·실제 휴대폰·결제사 연동 완료는 별도입니다. 이 작업 환경에는 팀 DB 비밀번호·토스 서버 키가 제공되지 않았고 연결된 Android 기기도 없어, 해당 외부 연동은 아직 검증하지 않았습니다.
