# ShareGuard 1.3 기능 수정 · 2026-10-05

## 적용 순서

1. 서버 관리자: Supabase SQL Editor에서 `ShareGuardAndroid/database/migrations/20261005_transactions_chat_notifications.sql` 전체를 실행합니다. **기존 `schema.sql`을 다시 실행하지 마세요.** 기존 회원·메시지·거래·결제 데이터를 지우지 않는 추가 마이그레이션입니다.
2. 앱: `ShareGuard-features-20261005.apk`를 기존 앱 위에 업데이트 설치합니다. 앱 삭제나 데이터 초기화는 필요 없습니다.
3. 로그인 후 알림 권한을 허용합니다. 이미 이름이 `이지수`로 저장된 계정은 **내 정보 → 닉네임 수정**에서 실제 사용할 이름으로 바꿉니다. 기존 회원의 이름은 임의로 변경하지 않았습니다.
4. 대여자·차용자 계정으로 아래 확인 항목을 점검합니다.

서버 코드로 배포하는 경우 동일 SQL을 `backend/src/main/resources/db/migration/V4__transactions_chat_notifications.sql`에도 제공합니다. Flyway 배포 시 자동 적용할 수 있으며, SQL Editor에서 먼저 적용한 경우에도 이 마이그레이션은 반복 실행할 수 있습니다. 기존 V1~V3는 수정하지 않습니다. V3의 서버 결제·QR·관리자 권한 제한을 유지합니다.

## 변경 내용

| 요청 | 반영 내용 |
| --- | --- |
| 진행 중 거래 삭제 | 결제 전 예약은 확인 후 취소하고 내 목록에서 숨깁니다. 취소 알림이 상대방에게 전달됩니다. 종료·거절·취소된 거래는 내 목록에서 삭제합니다. 결제·대여·분쟁 처리 중에는 반납/환불 처리를 먼저 완료하도록 안내합니다. 결제 기록을 직접 삭제하지 않습니다. |
| 예약이 있어도 추가 예약 | 예약을 각각 독립적으로 관리합니다. 같은 물품도 확정된 예약과 날짜가 겹치지 않으면 추가 신청할 수 있습니다. 다른 물품 예약에는 영향을 주지 않습니다. 같은 계정의 동일 기간 중복 클릭은 서버가 차단합니다. |
| 채팅에서 예약 날짜 조율 | 예약별 채팅에서 시작일·종료일 변경을 제안합니다. 상대방이 수락해야 일정·대여료·계약 초안이 함께 변경됩니다. 본인 수락, 제3자 처리, 이미 처리된 요청, 겹치는 확정 일정, 결제 중 변경을 차단합니다. 현재는 결제 전 변경을 지원합니다. |
| 등록 사진 대신 샘플 표시 | 저장된 `item_images`를 조회하여 홈·내 물품·상세·거래 화면에 실제 사진을 표시합니다. 상세에서 추가 사진을 볼 수 있습니다. 사진 선택/카테고리 변경 중 입력값을 보존하고, 새 등록은 사진 저장이 끝난 후에만 공개합니다. |
| 모든 이름이 이지수 | 회원가입에 닉네임 입력을 추가했습니다. 물품 소유자·채팅 상대방의 실제 프로필을 조회합니다. 기존 잘못된 이름은 본인이 수정할 수 있습니다. |
| 채팅방 밀어서 삭제 | 예약별 실제 채팅방을 표시합니다. 왼쪽으로 밀고 확인하면 내 목록에서 숨깁니다. 상대방 대화와 거래는 유지되고 상대방의 새 메시지가 오면 다시 나타납니다. 예약 카드에서도 대화를 다시 열 수 있습니다. |
| 채팅·대여 알림 | 서버에서 상대방별 알림을 생성합니다. 대여 신청/승인/취소/결제/대여 시작/반납, 채팅, 날짜 변경 요청/응답을 알립니다. 앱 알림함과 Android 알림을 연결하고 해당 거래로 이동합니다. |

## 알림 동작 범위

- 앱이 열려 있으면 약 8초 간격으로 새 알림을 확인하고, 열린 채팅은 약 5초 간격으로 갱신합니다. 입력 중인 메시지는 갱신으로 지워지지 않습니다.
- 앱이 백그라운드에 있으면 Android JobScheduler의 15분 주기 작업으로 확인합니다. 절전·네트워크·강제 종료 상태에 따라 늦어질 수 있습니다. **앱 종료 상태의 즉시 FCM 푸시는 이번 구현에 포함되지 않습니다.** 이를 추가하려면 Firebase 프로젝트 및 서버 푸시 자격 증명 연결이 필요합니다.
- 알림 권한을 거부해도 서버 알림함에는 기록이 남습니다. 알림 설정에서 권한을 변경할 수 있습니다.
- 테스트 로그인·알림 발송을 위해 운영 계정의 비밀번호나 서비스 역할 키를 소스에 넣지 않았습니다.

## 서버 설정과 기존 기능

- 검토용 APK는 마지막으로 지도 인증 200을 확인한 APK의 공개 설정 8개(Supabase, 카카오, 토스 승인 URL, PASS/PortOne)를 추출해 동일하게 빌드합니다. 기존 `local.properties`의 연결값은 덮어쓰지 않으며, Lint 오류를 없애기 위해 SDK 경로의 콜론 표기만 이스케이프했습니다.
- 카카오 서명 키는 기존 로컬 debug keystore를 그대로 사용합니다. 앱 버전은 1.3 / versionCode 4입니다.
- 토스 `TOSS_SECRET_KEY` 미설정은 별도의 서버 환경변수 문제입니다. 이 업데이트에서 키를 임의 생성하거나 결제를 성공 처리하지 않습니다.
- 채팅 알림/일정 합의/삭제를 사용하려면 서버 SQL 적용이 필요합니다. APK 설치만으로 서버 변경이 적용되지는 않습니다.

## 재현 가능한 검증

프로젝트 루트에서 Java 17 / Android SDK 환경으로 실행합니다.

```powershell
python tools/prepare_review_build.py
& 'C:\Program Files\Java\jdk-17\bin\java.exe' -classpath 'ShareGuardAndroid\gradle\wrapper\gradle-wrapper.jar' org.gradle.wrapper.GradleWrapperMain -p ShareGuardAndroid '-PshareguardConfig=build/review-20261005/app.properties' :app:testDebugUnitTest :app:assembleDebug :app:lintDebug --offline --console=plain
python tools/test_feature_database.py
```

`prepare_review_build.py`는 검증했던 APK가 있는 현재 PC용 빌드 준비 도구입니다. 다른 PC에서는 프로젝트의 공개 연결 설정을 `local.properties`에 넣고 `-PshareguardConfig` 옵션을 생략하세요. 시크릿 키는 넣지 않습니다.

DB 테스트는 Windows PostgreSQL 18 도구로 프로젝트의 `build/feature-db-tests` 아래에 격리된 DB를 만들고 localhost:55435에서 실행합니다. Supabase 운영 DB에는 연결하지 않으며 완료 시 테스트 서버를 종료합니다.

## 두 계정으로 확인할 흐름

1. 서로 다른 닉네임의 회원 두 명으로 로그인하여 각자 이름과 상대방 이름이 구분되는지 확인합니다.
2. 사진 두 장으로 물품을 등록하고 앱을 다시 열어 홈/상세에서 실제 사진이 표시되는지 확인합니다.
3. 같은 물품을 서로 겹치지 않는 두 기간으로 예약합니다. 각 예약의 채팅이 분리되는지 확인합니다.
4. 채팅에서 날짜 변경을 제안하고 상대방으로 수락합니다. 예약 카드와 결제 예정액이 변경되는지 확인합니다.
5. 결제 전 거래를 취소/삭제하고 상대방의 취소 알림을 확인합니다.
6. 채팅방을 왼쪽으로 밀어 삭제합니다. 상대방이 새 메시지를 보내면 다시 나타나는지 확인합니다.
7. 상대방 계정의 앱 알림함, 시스템 알림, 알림을 눌렀을 때 거래 이동을 확인합니다.

2026-10-05 사용자가 Supabase SQL Editor에서 이 기능 SQL의 `Success. No rows returned` 결과를 확인했고, 로컬 기능 APK 1.3을 연결된 S25 Ultra에 업데이트 설치했습니다. 이는 실제 두 계정 간 전체 흐름이나 외부 결제·PASS 검증을 완료했다는 뜻은 아닙니다.

GitHub 반영 시 원격 브랜치의 최신 서버 기능을 함께 병합했습니다. 병합본은 앱 빌드·단위 테스트·Lint, 기존 V1~V3 적용 후 새 SQL을 두 번 실행하는 로컬 PostgreSQL 통합 검사를 거쳤습니다. 이 병합본 APK의 실기기 재설치·두 계정 검증은 별도로 필요합니다.

병합본 검증 결과: Android 테스트 21개, 서버 테스트 35개(로컬 DB·서버 기동 포함), 기능 DB 검사 26개, 비밀번호 복구 테스트 8개 통과. Android APK와 서버 bootJar 빌드 성공, Lint 오류 0개입니다. 서버 통합 검사에서 Flyway V1~V4 적용과 기존 결제·QR 권한 제한도 확인했습니다.
